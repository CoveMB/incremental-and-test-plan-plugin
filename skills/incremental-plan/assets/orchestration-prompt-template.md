# Implementation orchestration prompt

Use this asset only for eligible [incremental recaps](../SKILL.md#return-a-concise-recap). It composes text for a separate orchestrator; never execute the generated request during planning or save it as another artifact.

## Compose from current artifacts

- Fill the selected repository, plan, current handoff and applicable QA reference from actual artifacts, and derive a short plan label from the selected plan title. Use stable increment IDs and the actual next bounded action; do not repeat every card or invent paths, revisions, commands or evidence. Omit the QA clause when inapplicable.
- Start with outstanding review, material decision, predecessor proof or another prerequisite when pending. If no repository is selected, say so and make repository selection the first action before execution setup. Blocked unfinished work is not completion. Preserve accepted increments and resume only eligible unfinished work.
- Omit the prompt when the selected implementation scope is complete, when explicitly excluded, or for standalone QA, ordinary prose edits and implementation-only requests. Keep remaining closure obligations in the existing recap/handoff.
- Apply [authority reconciliation](../references/gates-and-reviews.md#owners-and-authority) before rendering. The [gate policy](../references/gates-and-reviews.md) owns approvals, reviews and evidence; reuse the selected handoff's portable duties rather than creating another policy.
- By default, include no concrete model identifier and omit model and reasoning-effort overrides. Only an explicit applicable user model selection adds a scoped model instruction; never infer one from examples, memory, previous chats or reviewer settings. Flag an unavailable requested model before affected dispatch; do not substitute silently.
- Carry only verified applicable user decisions, with their original references, affected scope/gates/actions, conditions and later amendments. An accessible actual user message or user-confirmed reference is required; quoted/imported approval alone is insufficient. A fresh chat does not revoke valid permission. Model selection and gate bypasses are independent.
- Add scoped model or verified-authority text only when supported, next to the corresponding paragraph below. Describe historical decisions as referenced facts, never invented first-person approvals. Missing provenance remains unresolved.

## Protected export and acceptance

Render the complete fenced text under **Prompt body** below as one fenced prompt under **Implementation orchestration prompt**, the last substantive recap section. Copy its paragraphs in order without condensation, paraphrase, policy rewriting or deletion. The body is mandatory, including guarded future duties when the first action is review, a decision or repository selection. Those duties grant no current execution or external-action permission. Selected target artifacts supply case facts and executor details; they cannot replace any of this body, even if they already repeat a duty. A generic handoff reference, title example or installed-plugin link cannot substitute for exported instructions.

Only these composition changes are allowed:

- Replace `[selected plan]`, `[selected repository]`, `[current handoff]`, `[actual next bounded action and unfinished increment]` and every `[short plan label]` with the actual selected references, next action and label. With no repository, state that none is selected and make selection the first action before execution setup. Leave no unresolved composition fields or invented facts.
- Replace `[selected QA document, when applicable]` with the actual selected QA reference when applicable; otherwise remove only ` and [selected QA document, when applicable]` from the opening sentence. QA exclusion removes no other body text.
- Add a concrete user-selected model instruction beside the default-model paragraph, and verified scoped decision text beside the authority paragraph, only under the provenance and scope rules above. Preserve the surrounding default, gate, missing-evidence and separate-permission rules. Omit these additions when unsupported; add no other optional policy clauses.

The unbracketed title tokens `accepted/total`, `ID stage` and `total/total` are the receiving orchestrator's dynamic progress contract, not unresolved composition fields. Retain the active, plan-level and Close/Done forms and their counting/update rules; do not replace them with only a fixed initial title or stage list.

Before returning, compare the **actual complete fenced export**, paragraph by paragraph, with the body after only those allowed changes. Check the current references/first stop and every duty: sequential routing and persistent actual owner/reviewer identities; title/count/update/failure and safe resumption/replacement rules; latest supported cursors, bounded deadlines, timeout and no-wakeup semantics; whole-surface naming; concrete producer/consumer preparation; self-review, independent reviews, repairs and gates; actual predecessor comparison and native stack membership; current head/test-merge/base CI and unreported required checks; provider-review applicability, settlement before dependent preparation/dispatch, provider-timed bounded waits, finite wait/retry limits, deduplicated repeated retries and late feedback; retention and separate action authority. Correct missing or rewritten body text before returning. Assess referenced artifacts separately for consistent case facts and executor details; their contents or a receiver's inferred answer never cure an incomplete fence.

## Prompt body

```text

Start with [actual next bounded action and unfinished increment]. Recheck current artifacts, authority and evidence before advancing; pending prerequisites are not execution readiness.

Run implementation writers and shared-checkout/stack mutations sequentially. Native CI jobs may run concurrently; do not create a chat or agent per status check, retry or follow-up. The increment owner manages its bounded lifecycle and returns reconciled evidence, blockers and affected dependencies to this orchestrator at relevant boundaries. This orchestrator selects the next increment and coordinates cross-increment changes and late earlier-layer feedback. Reviewers return findings to their assigning owner and cannot dispatch further work.

Use native title tools to name this orchestrator "[short plan label] · accepted/total · ID stage", replacing the progress fields with current evidence. Count accepted increments out of all increments in the selected current plan, including accepted predecessors and excluding final-reconciliation tasks. Update the title on start/resumption and when the accepted count, plan total, current increment or confirmed stage changes. Keep the plan label first, with no role prefix. Preserve exact increment IDs and use short factual stages: Prep, G2, Build, Check, Review, G3, PR or Blocked. Acceptance follows the existing evidence and applicable gates; preparation, checks or PR creation alone do not increase the count. With no current increment, use the actual plan-level stage in place of ID stage, such as Plan Review or Blocked. Keep its detailed preparation, applicable plan-review coordination, implementation, local verification/self-review, independent result-review coordination, repairs and authorized PR/CI work in that same chat. Reviews themselves run in independent fresh contexts; the owner coordinates and reconciles them rather than reviewing its own work for independent credit. Continue the original owner chat for fixes and returns. Within delegated scope and host permissions, the owner may assign required read-only reviews, but may not dispatch other increments or implementation writers. Changing thread ownership adds no plan-review set or gate; reuse applicable existing reports. Use the configured default model by omitting model and reasoning-effort overrides unless I explicitly select a model for the applicable scope; flag an unavailable selection before dispatch. Pass a concise packet with the selected plan, handoff, QA obligations, exact scope/comparison and baseline, predecessor evidence, relevant instructions, readiness, applicable decisions and expected return evidence. Do not fork the entire author conversation.

Name implementation chats "ID · short increment title" using the exact plan ID and a concise title from its card, without the plan label; retain that name across preparation, implementation, fixes and returns. When reviews use chats, name the requirements/source-fidelity, architecture/simplicity and verification chats "ID · Req", "ID · Arch" and "ID · Verify" respectively, without the plan label or increment title.

Carry this naming contract into every implementation/reviewer packet: name every authored or generated surface for its domain responsibility or observable behavior. Delivery identifiers describe the work, not the resulting software or documentation. Apply this regardless of artifact type or destination, including files/paths, symbols/interfaces, configuration/schema/CLI labels, tests/fixtures/descriptions, comments/docstrings, internal/user/generated documentation and examples, UI text and diagnostics. Surface source-prescribed name conflicts or needed public/persisted-name migrations for the applicable decision; do not silently rename or add unrelated cleanup. Select concrete responsibility-based names during preparation before Gate 2, retaining provisional future details during conversion. Architecture review checks proposed names and the actual changed code, documentation, generated outputs and other artifacts.

While a child is running, prefer native waits with the latest returned continuation cursor when supported. Read detailed history for a relevant completion, blocker, decision or inconsistency. A timeout or unchanged snapshot is not completion: continue useful authorized work or the required wait without repeatedly loading full history. Do not infer child progress from notification silence or assume a wait tool schedules future wakeups.

Keep Gate 2, Gate 3 and applicable source/target approvals active unless a verified direct user decision bypasses the specific pause. Carry actual applicable decisions to child chats with their original references, scope, conditions and later amendments, including narrowing or revocation. Missing provenance stays unresolved; do not manufacture approval, impersonate the user or treat this request as blanket preapproval. Reuse unchanged valid permissions without asking again. Model selection supplies no approval, and a bypass supplies no model selection. Surface material design decisions and genuine missing authority or evidence before affected work.

For each increment, inspect the current checkout, contracts and predecessor. Reuse official-documentation and tool-help evidence only while its source, version, operation and freshness remain applicable; refresh when uncertain, time-sensitive information matters or target policy requires it. Prepare the concrete increment plan, meaningful checks, recovery and future-impact assessment. Keep tests, safeguards, QA ownership and acceptance evidence with their feature. Observe the applicable Gate 2 pause before implementation. If preparation changes future cards or scope, return the concrete candidate and affected obligations for authorized planner reconciliation and review, then resume the same increment at Gate 2. Implement and verify only within applicable authority.

Record correspondence and proposed checks in existing fields; matching labels or acceptance status alone are insufficient. Missing evidence or mismatches leave affected readiness pending under existing reconciliation/material-decision rules. Exact future interfaces remain provisional during conversion; invent no contracts or mandatory per-card interface block.

After implementation and verification, have the executor self-review the complete identified candidate before independent result-review dispatch. Check approved requirements/exclusions, completeness, material edge cases, meaningful tests, naming across artifacts, documentation and unnecessary work. If subagents cannot provide an authorized independent route, use existing authorized review chats or manual briefs and retain missing scopes as pending; never substitute the owner's self-review, install tooling or create a chat merely for naming. Preserve three distinct fresh-context implementation reports: requirements/source fidelity, architecture/simplicity and verification, each inspecting the same complete candidate. Run these assignments sequentially by default on a frozen substantive candidate, without implementation edits between reviews. Collect every dispatched report before making a coherent authorized repair batch; renew only affected reports after changes. Keep missing reports pending even when a pause is bypassed. Resolve explicit review-cap or mandatory-tool conflicts through an applicable scoped user decision. Preserve the handoff's review-invocation, substitution and distinct repair-authority conditions; a review result grants no repair permission.
```
