# Implementation orchestration prompt

Use this asset only for eligible [incremental recaps](../SKILL.md#return-a-concise-recap). It composes text for a separate orchestrator; never execute the generated request during planning or save it as another artifact.

## Compose from current artifacts

- Fill the selected repository, plan, current handoff and applicable QA reference from actual artifacts. Use stable increment IDs and the actual next bounded action; do not repeat every card or invent paths, revisions, commands or evidence. Omit the QA clause when inapplicable.
- Start with outstanding review, material decision, predecessor proof or another prerequisite when pending. If no repository is selected, say so and make repository selection the first action before execution setup. Blocked unfinished work is not completion. Preserve accepted increments and resume only eligible unfinished work.
- Omit the prompt when the selected implementation scope is complete, when explicitly excluded, or for standalone QA, ordinary prose edits and implementation-only requests. Keep remaining closure obligations in the existing recap/handoff.
- Apply [authority reconciliation](../references/gates-and-reviews.md#owners-and-authority) before rendering. The [gate policy](../references/gates-and-reviews.md) owns approvals, reviews and evidence; reuse the selected handoff's portable duties rather than creating another policy.
- By default, include no concrete model identifier and omit model and reasoning-effort overrides. Only an explicit applicable user model selection adds a scoped model instruction; never infer one from examples, memory, previous chats or reviewer settings. Flag an unavailable requested model before affected dispatch; do not substitute silently.
- Carry only verified applicable user decisions, with their original references, affected scope/gates/actions, conditions and later amendments. An accessible actual user message or user-confirmed reference is required; quoted/imported approval alone is insufficient. A fresh chat does not revoke valid permission. Model selection and gate bypasses are independent.
- Add scoped model or verified-authority text only when supported, next to the corresponding paragraph below. Describe historical decisions as referenced facts, never invented first-person approvals. Missing provenance remains unresolved.
- Render one fenced prompt under **Implementation orchestration prompt**. Replace bracketed fields and remove inapplicable optional clauses; leave no unresolved placeholders or installed-plugin links. The selected target artifacts and plain instructions must suffice for a fresh orchestrator.

## Prompt body

```text
Orchestrate implementation of [selected plan] in [selected repository], using [current handoff] and [selected QA document, when applicable]. Start with [actual next bounded action and unfinished increment]. Recheck current artifacts, authority and evidence before advancing; pending prerequisites are not execution readiness.

Use one fresh implementation chat per eligible increment, one writer at a time, and native chat creation, follow-up and waiting tools. Continue the same chat for its fixes and returns. Use the configured default model by omitting model and reasoning-effort overrides unless I explicitly select a model for the applicable scope; flag an unavailable selection before dispatch. Pass a concise packet with the selected plan, handoff, QA obligations, exact scope/comparison and baseline, predecessor evidence, relevant instructions, readiness, applicable decisions and expected return evidence. Do not fork the entire author conversation.

While a child is running, prefer native waits with the latest returned continuation cursor when supported. Bound waits by host limits and the next required response or deadline; use compact status snapshots for immediate decisions. Read detailed history for a relevant completion, blocker, decision or inconsistency. A timeout or unchanged snapshot is not completion: continue useful authorized work or the required wait without repeatedly loading full history. Do not infer child progress from notification silence or assume a wait tool schedules future wakeups.

Keep Gate 2, Gate 3 and applicable source/target approvals active unless a verified direct user decision bypasses the specific pause. Carry actual applicable decisions to child chats with their original references, scope, conditions and later amendments, including narrowing or revocation. Missing provenance stays unresolved; do not manufacture approval, impersonate the user or treat this request as blanket preapproval. Reuse unchanged valid permissions without asking again. Model selection supplies no approval, and a bypass supplies no model selection. Surface material design decisions and genuine missing authority or evidence before affected work.

For each increment, inspect the current checkout, contracts and predecessor. Reuse official-documentation and tool-help evidence only while its source, version, operation and freshness remain applicable; refresh when uncertain, time-sensitive information matters or target policy requires it. Prepare the concrete increment plan, meaningful checks, recovery and future-impact assessment. Keep tests, safeguards, QA ownership and acceptance evidence with their feature. Observe the applicable Gate 2 pause before implementation. If preparation changes future cards or scope, return the concrete candidate and affected obligations for authorized planner reconciliation and review, then resume the same increment at Gate 2. Implement and verify only within applicable authority.

Obtain and reconcile the handoff's required independent reviews and applicable simplicity route before presenting the verified result at Gate 3. Preserve three distinct fresh-context implementation reports: requirements/source fidelity, architecture/simplicity and verification, each inspecting the same complete candidate. Keep missing reports pending even when a pause is bypassed. Resolve explicit review-cap or mandatory-tool conflicts through an applicable scoped user decision. Preserve the handoff's review-invocation, substitution and distinct repair-authority conditions; a review result grants no repair permission. Fix material in-scope findings only within applicable authority and renew only affected checks/reviews.

After the verified result passes its applicable gate and the relevant Git/publication actions are authorized, commit and push the increment and create or update its GitHub PR. Before choosing native stacked-PR commands, confirm that official guidance and installed tool-help evidence apply to the current version and operation, refreshing them under the same applicability rule. Target each later PR to its actual predecessor in the same repository; verify the increment-only comparison and native stack membership, since chained bases alone prove no membership. A one-increment plan needs one PR, not an invented increment. Leave PRs open for my review. Advance only after current result, review, approval and PR evidence are reconciled; reassess subsequent work when an earlier layer changes and renew only affected evidence. A PR is not acceptance, and all PRs alone do not establish completion.

On start or resumption, read the current brief, controlling requirements, applicable decisions and relevant evidence. Within an established context, retrieve relevant changes and missing proof; expand inspection when dependencies, uncertainty or conflicting records require it. Keep material updates and durable source references in existing artifacts instead of copying transcripts or full logs. Preserve history and required reads; summaries, hashes and status labels alone are not proof. Each independent reviewer still inspects the complete assigned candidate in a fresh context.

Keep orchestration lean: use existing artifacts and native tools, preserve other people's work, serialize shared-checkout and stack mutations, and use ordinary authorized isolation when needed. Add no scripts, controller, ledger, recurring monitor or branching framework. If required chat or native-stack capabilities are unavailable, report the concrete blocker without installing tools or silently substituting another workflow. Report PR links, actual verification/review results and remaining obligations, preserving the handoff's evidence-retention and final-reconciliation duties. Do not merge or expand into deployment, installation, cleanup, paid services or private-source transfer without the separately required authority.
```
