## Verification implementation work

Extend existing C16 and affected handoff/continuation cases in `tests/scenarios.md`, with raw fixture/request material separated from evaluator expectations. Do not add a runtime runner, framework, live provider or tests that merely match policy sentences. Keep simulated decisions, synthetic skill invocation, actual Ponytail integration and native activation distinctly labeled.

The future executor first confirms the README's supported validator locations and installed dependencies without installing anything. Run its two per-skill `python3 -B .../scripts/quick_validate.py ...` checks, parsed manifest/frontmatter/containment/resource/link checks, whitespace checks and delivered-file privacy/dependency inspection against the settled candidate. The legacy whole-package helper is not currently established by these checks; do not rename local validation as an equivalent official pass. Commands using unresolved validator paths remain provisional until that inspection.

Behavioral evaluations need separate explicit live-model authority. Use existing fresh-agent facilities and disposable synthetic fixtures; no new test runner. The controller owns expected outcomes, action inspection and preservation, while evaluated agents receive only raw inputs and the candidate. Bound output and work to the selected fixture; no product tests, global edits, installation, provider use, external review or recursive delegation. Reuse useful existing case results only when candidate/scope correspondence holds. No chosen number of scenarios proves overall quality.

Actual integration with the installed Ponytail skill requires applicable explicit authority under the current instructions until those instructions are amended. A later actual check must identify the real loaded skill, selected candidate and read-only report; it does not establish another host, automatic desktop activation or universal routing. Do not execute it merely to finish this planning task.
